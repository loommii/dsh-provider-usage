# 发布流程（规范性文件）

> 规定每一次**发布**怎么操作、红线是什么。版本号怎么定（三段式）见 `版本号说明.md`。
> CHANGELOG 位于 `docs/CHANGELOG.md`（v0.4.2 起从仓库根目录迁入）。

## 1. 流程（每次发布完整走一遍）

```
1. 按版本号说明.md 决定本次的新版本号
2. 本地开发 + 你在本机验收（只改代码，不提交）
3. 更新 package.json 版本号 + docs/CHANGELOG.md（同一提交内完成）
4. 提交 + push main
5. 打 tag：git tag v<版本号> && git push origin v<版本号>
6. （可选）写发布说明 / release notes
```

**核心原则**：tag 指向的提交必须**已经包含**版本号与 CHANGELOG 变更（即第 3、4 步先于第 5 步，且都进同一次提交）。
**红线**：未经本地验收的改动不得推送 main。历史 0.1.x 早期提交例外（已归档说明）。

## 2. 提交信息与 CHANGELOG 约定

| 类型 | 提交前缀 | CHANGELOG 分类 |
|---|---|---|
| 破坏性变更 | `feat!:`（或 `fix!:`） | 置顶 `BREAKING` 说明 |
| 功能（大） | `feat:` | 「大功能」节 |
| 功能（小） | `feat:` | 「小功能」节 |
| 修复 | `fix:` | 「修复」节 |
| 文档/规范 | `docs:` / `chore:` | 不入版本号，可顺带记录 |

## 3. Tag 规则（两态）

| 状态 | 规则 |
|---|---|
| **未公开**（还没告诉任何人、未上 release 页） | 允许删除重建：`git tag -d v0.2.0 && git push origin :refs/tags/v0.2.0` |
| **已公开**（发布说明 / 已告知使用者） | **不可变**：只新增不修改，出问题发新 PATCH |

- tag 名称一律 `v` + 三段版本号（如 `v0.2.0`）；
- 一个版本 = 一个 tag，指向该版本发布前的最后一次提交。

## 4. 固定版本安装（给别人/别的机器）

```sh
dsh plugin --profile web add github:loommii/dsh-provider-usage#v0.2.0
```

本地开发始终用 `link:` 模式（跟随 working tree，无版本概念）。

## 5. 发布时文件同步（必须同一提交）

| 文件 | 动作 |
|---|---|
| `package.json` 的 `version` | 改成新版本号（三段，npm 强制） |
| `docs/CHANGELOG.md` | Unreleased 条目按 大功能/小功能/修复 归档（自 v0.4.2 起位于 docs/ 目录） |
| git tag | 提交后打 `v<新版本>` 并推送 |
| `docs/规范/` | 规则性变更才需要动 |

## 6. 发布检查清单（提交前过一遍）

- [ ] 本地验收通过（用量卡片、设置页提供方管理、卡片拖动/位置记忆）
- [ ] `node --check` lib 两个文件
- [ ] `npm test`（host 87 + secure-store 9 + smoke）通过
- [ ] package.json 版本号 = CHANGELOG 条目 = tag 版本号，三者一致
- [ ] 版本号与 CHANGELOG 变更在**同一次提交**内（tag 指向它）
- [ ] 工作区无未纳入提交的文件（`git status` 干净）

## 7. FAQ（发布操作）

**Q：改了 client 只硬刷新，改了 host 要重启？**
A：对。client.js 改完浏览器 Cmd+Shift+R；lib/index.js 改完重启 `dsh web`。

**Q：发布后发现严重 bug？**
A：按 bugfix 流程发新 PATCH（0.2.0 → 0.2.1），不回改已公开的旧 tag。

**Q：tag 打错了（位置/版本号不对）？**
A：未公开 → 按 §3 删除重建；已公开 → 不可变，按错误后果补发说明或新版本。

**Q：这个改动算大功能还是小功能？**
A：判不了就归入功能（MINOR），CHANGELOG 里写清楚条目即可；大小判断标准见版本号说明.md §2.1。
