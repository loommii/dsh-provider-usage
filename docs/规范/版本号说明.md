# 版本号说明（规范性文件）

> 规定本项目版本号的**语义与递增规则**。发布操作见 `发布流程.md`。
> 自 **v0.2.0** 起强制执行；此前 0.1.x 为早期逐批递增，见 §5 历史对照。

## 1. 版本号格式

语义化版本（Semantic Versioning）**三段式**：

```
MAJOR.MINOR.PATCH
```

例：`0.2.0`、`1.4.2`。`package.json` 的 `version` 是唯一实际生效的版本号。

### 1.1 为什么不是四段（评估结论，2026-08-24 定案）

- npm/pnpm 生态强制 semver 三段，实测：`version: "0.2.0.0"` 直接报
  `ERR_PNPM_BAD_PACKAGE_JSON: Invalid version`，四段号会导致插件无法安装；
- 主流生态（npm、GitHub Release、DSH 插件机制）均按三段工作；
- "大功能/小功能"的区分**不进版本号**，改用 CHANGELOG 分类表达（见 §2.1）——这是主流做法（Conventional Commits）。

## 2. 递增规则（唯一决策依据：兼容性）

| 版本位 | 何时 +1 | 示例 |
|---|---|---|
| **PATCH**（修订） | 只修 bug，不新增、不破坏任何行为 | 对话框悬空、右缘越界、被浮层遮挡 |
| **MINOR**（次版本） | 任意功能（大功能与小功能都算），向后兼容 | 设置页、精灵动画、挂载方式重构、样式重构 |
| **MAJOR**（主版本） | 破坏性变更；或 1.0.0 稳定里程碑 | 接口/协议不兼容 |

递增小位后低位归零：`0.2.3 → 0.3.0（新功能）→ 0.3.1（修 bug）→ 1.0.0（稳定）`。

### 2.1 大功能 / 小功能怎么表达（不占版本位）

- 版本号只分「功能 MINOR / 修复 PATCH」，**不区分功能大小**；
- 大小之分留在 **CHANGELOG.md**：每版按「大功能 / 小功能 / 修复」三节列出；
- 提交信息约定：`feat!:` 破坏性功能、`feat:` 功能、`fix:` 修复；
- 大/小功能判定（主观，记录即可）：影响面广 / 改动量大 / 用户可见能力成体系 → 大；单点增量 → 小。

### 2.2 0.x 阶段特殊规则（当前处于 0.x）

- 0.x 的 **MINOR** = 功能里程碑（相当于 1.0 前的主版本移动：0.1 → 0.2 → 0.3…）；
- 0.x 的 **PATCH** 仅限纯 bugfix；
- 破坏性变更在 0.x 下可直接 +MINOR 并标注 `BREAKING`，由维护者判定；
- **1.0.0 目标**：功能覆盖方案 M2 里程碑、文档齐全、安装即用、有验收记录。

## 3. 判定规则（bugfix vs feature）

- 只修正错误表现 → PATCH；
- 新增/调整用户可见能力 → MINOR；
- 拿不准 → 问使用者（本项目即你本人），并如实记入 CHANGELOG 对应节。

## 4. 发布时版本号动作（简表）

| 场景 | 版本位 | 例子 |
|---|---|---|
| 修 bug | PATCH+1 | 0.2.0 → 0.2.1 |
| 加功能（大或小） | MINOR+1 | 0.2.1 → 0.3.0 |
| 破坏性变更 | MAJOR+1（0.x 下可 MINOR+1 + BREAKING） | 0.3.0 → 1.0.0 |

## 6. FAQ（版本语义）

**Q：什么时候到 1.0.0？**
A：功能覆盖方案 M2 里程碑、稳定运行、文档齐全时，由你决定。

**Q：大功能和小功能在版本号上怎么区分？**
A：不区分。二者都走 MINOR；大小之分见 CHANGELOG 的「大功能 / 小功能」节。

**Q：不能改四段吗？**
A：不能进 package.json（pnpm 实测报 Invalid version）。若只做展示标签双轨，与包里版本会两套漂移，评估后否决（2026-08-24 定案）。

**Q：已打 tag 的版本能改吗？**
A：两个状态：**未公开**可删除重建（命令见发布流程.md §3）；**已公开**后只增不改，出问题发新 PATCH。
